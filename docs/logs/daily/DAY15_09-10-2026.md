## The industrial-overlap bug

`04_extract_industrial_area.py` measured a buffer's industrial area as
`clipped_geom.area.sum()` — summing each polygon's clipped area independently.
OSM maps some industrial land more than once (around station 5627 the estate
"Okhla Ph III" appears as two identical 418,465 m² polygons), so shared land was
counted twice. Overlap is 2.6% of total industrial area in the Delhi extract.

It inflated a feature the model was **trained on**, at 5 of 42 stations — worst
cases 5627 at 0.4481 against a true 0.3147 (+42%) and 6960 at 0.1167 against
0.0698 (+67%).

**Why it survived QC for months, and the lesson.** `05_qc_industrial.py`
hard-fails on `fraction > 1`. With 42 stations none ever crossed it. The
2,388-cell grid is 57× the sample and produced a cell at 1.06, tripping the gate
immediately. The QC was right all along — it just needed a bigger sample. *A
threshold that has never fired is not evidence that it never will.*

Muhammed chose to fix it and re-run rather than keep train/serve consistency and
document (option A over option B). The correction is essentially free:

| spatial LOSO | was | now |
|---|---|---|
| R² | 0.8031 | **0.8018** |
| within-R² | 0.7207 | 0.7156 |
| RMSE µg/m³ | 33.73 | 33.84 |
| conformal q (90%) | 0.5514 | 0.5497 |
| stations below coverage target | 15 | **18** |

**A methodological decision worth flagging.** Keeping the old hyperparameters on
the corrected data scored **0.8035** — better than the re-tuned 0.8018. The
re-tuned figure is kept deliberately: choosing between two hyperparameter
searches by their spatial-LOSO score would reintroduce the test set into model
selection, which is exactly what the block-nested design exists to prevent.
Tuning is seeded, so a fresh clone reproduces 0.8018. The tuning stage was
unfrozen rather than left pinned, because a frozen tuning stage would quietly
break the repo's "reproduces end to end" claim.

## Decisions taken alone, with alternatives

- **1 km, not the planned 5 km slice.** A 5 km extraction produces 1 km-buffer
  features sampled every 5 km — a sparse point sample, not an areal mean, and
  the download design says coarse products are *aggregated* from 1 km cells.
  The slice had already paid for itself. *Rejected:* extract 5 km then redo at
  1 km, two GEE runs for information the first had produced.
- **Batching added to existing extractors, never as copies.** A second copy of a
  feature definition would drift. Default off, so station stages are untouched.
  *Rejected:* prediction-specific extractor scripts.
- **Every batched path verified against the 42 committed station values before
  use.** This caught a first batched-SRTM attempt that read a point value where
  the station script uses a 1 km buffer **mean** — off by up to 7 m. Verified
  versions reproduce to 1e-9 (SRTM), exactly (WorldCover's 12 class counts), and
  3,066/3,066 rows to 1e-12 (NDVI).
- **Per-cell gap-fill calibrations, not borrowed from the nearest station.** The
  method *is* "calibrate at the location you are filling". Borrowing would make
  a cell's AOD depend on its distance from a monitor. *Rejected:* nearest-station
  coefficients.
- **One shared master-table builder**, gaining an optional `--base_table` because
  the grid has no PM2.5 target to define its rows. *Rejected:* a separate
  assembly script, which would have duplicated the NDVI `merge_asof` period join
  — a feature-defining operation.
- **QC bounds overridden, not suppressed**, where station-calibrated thresholds
  are too tight for the grid: a cell at 301.0 m failed a [150, 300] ceiling set
  from 42 urban stations spanning 199.7–271.7 m. It sits on the Aravalli ridge
  and the reading is real, so the grid stage uses 350 m. *Rejected:* removing the
  check, or loosening it for training too.

## Things I got wrong, and what corrected them

- **Overpass.** Four failed attempts before switching to a pre-built Geofabrik
  extract. The decisive evidence arrived early — `out ids` succeeded on the same
  tile where `out geom` returned 504, which already proved the gateway was
  refusing large *responses* rather than timing out on computation. I tuned tile
  size twice more before accepting it.
- **Geofabrik Northern Zone alone.** It excludes Uttar Pradesh, costing 57 power
  plants (including Dadri) and 24% of roads in the Noida/Ghaziabad strip *inside*
  the study bbox. Both would have produced plausible wrong numbers with no error
  anywhere. Caught only by diffing against the training export.
- **MAIAC retry logic.** Retried an identical request four times with backoff on
  the 5000-element error, which is deterministic — the same request can never
  succeed. Replaced with adaptive halving; only 5 of 288 chunks needed it.
- **NDVI diagnosis.** I blamed a 75M-pixel `reduceRegions`. Measurement showed it
  scales sub-linearly; the real cost was `station_fc.geometry().bounds()`, a lazy
  union of 2,388 polygons re-evaluated on all 73 periods. The run was slow, not
  hung, and grep's buffering hid its progress.
- **Extrapolation figure.** I reported 37% of cells outside the training range;
  that was land-use features only. Across all numeric features it is 56%.
- **Near-miss in git.** 549 MB of pbf and 16 MB of chunk cache were about to be
  committed, and a hand-written `.gitignore` had *overwritten* DVC's generated
  one, which would have committed a DVC-managed output and desynchronised the
  two. Caught while staging.

The common thread in the first four: acting before the evidence was exhausted.
The counterweight that caught every real problem was comparing against committed
station values *before* trusting anything.

## Later the same day — steps 7, 8 and 9 (the plan is now complete)

**Step 7 — the real grid is served.** `/api/predict` returns the cell containing the
point, not the nearest station. Muhammed's reasoning: *"that's why we build a model —
if we are giving the value of the nearest cell why do we need a model"*. Connaught
Place reads 204.5 µg/m³ from its own cell while the monitor 2.6 km away observed 223.8
and the model predicts 206.9 there. `/api/grid` serves 2,388 real cells in ~70 ms;
`synthetic: true` is gone. All 365 dates are now servable, up from 346 — the extra 19
had no usable monitor reading so never entered training, but the satellite and
meteorology inputs exist, and refusing them would withhold estimates for a gap in the
*ground truth*, which is the gap a satellite model exists to fill.

**Step 8 — aggregation, and ρ measured properly.** ρ is the same-day correlation
between two locations' prediction errors; it decides how much an areal mean's interval
may shrink. Re-measured across all 861 station pairs: **ρ = 0.050, CI [0.022, 0.085]**,
higher than the published 0.032.

Three findings, one of which overturned a recommendation I had already given:

1. ρ is higher than published.
2. I expected re-running on all 42 folds to fix the thin close-pair sample. **It did
   not** — still exactly 8 pairs under 2 km, because that is Delhi's station geometry,
   not a limitation of my method.
3. **ρ does not decay with distance** (p = 0.62). It is a whole-day effect: on
   2025-05-22, 35 of 38 stations erred the same way by −29%, against 60% / −3% on a
   typical day.

Finding 3 killed my own argument for using the close-pair ρ = 0.130 ("the right
distance"). If ρ does not vary with distance, close pairs are not better targeted —
they measure the same quantity with n=8 instead of n=861, and bootstrapped over
stations, 0.130 falls outside the honest CI. Muhammed chose the point estimate with
the CI carried through into every row.

A floor follows from finding 3: a whole-day error cannot be averaged away, so
shrinkage bottoms out at √ρ = 0.224. 10 km is already at 0.244, so **aggregating
beyond ~5 km buys almost nothing**.

**Step 9 — three download products.** Stations (measured + features), 1 km grid
(features, **verified reproducible**: all 2,388 rows re-predict to within 0.005 µg/m³),
and coarse grids (areal means, **no features** — averaged features cannot reproduce
averaged predictions through a nonlinear model, so omitting them makes the error
impossible rather than merely documented).

The caveat that most needed landing: a 5 km interval of ±16% reads as *better data*.
It is not. A real 5 km cell reports 282.9 µg/m³ ±16% while its 25 constituent 1 km
cells span **201 to 327** — the lowest falls outside the coarse interval entirely. The
tighter number describes the area *average*; individual streets vary for real reasons.
Stated in `ATTRIBUTION.txt` of every coarse bundle, the `/columns` response, and the
UI, because one place is not enough for something this easy to misread.

## UI rework, after the plan was done

Muhammed asked for two things: let the map show every resolution, and simplify a
screen that had become a wall of prose with awkward gaps.

**Multi-resolution map.** `/api/grid` takes `resolution_km` and serves 1, 2, 5 or
10 km — 2,388 / 605 / 105 / 29 cells at ±55.0% / 29.5% / 16.3% / 13.4%.

**A reference page instead of a wall of text.** The main screen is now map, readout,
compact AQI legend and four model numbers; everything explanatory moved to
`/about.html`. The page went from 608 lines of mostly prose to a 22 KB screen plus a
13 KB reference page.

**One deliberate departure from the instruction.** Explanations moved out, but
warnings that change what the *current* number means stayed inline, shown only when
they apply — switching to a coarse resolution, and querying a cell outside the
training range. Muhammed's point that these already ship with downloads is right, but
someone reading the map may never download anything, and the misreading happens at the
moment the number changes.

**Then three bugs, two of them mine and found by Muhammed:**

- The extrapolation warning never cleared — clicking a valid cell left the previous
  warning on screen, so a cell *inside* the training range looked like it was outside.
  A stale warning is worse than none; it makes the flag untrustworthy everywhere.
- Table headers were left-aligned over right-aligned numbers: the rule was
  `td.num{text-align:right}`, which targets `td` only, so `th.num` stayed left.
- The reset-view button's icon was invisible in dark mode — I themed it `var(--ink)`
  (white) on Leaflet's permanently-white control background.

**And a fourth that only testing caught:** the reset button silently didn't work.
`fitBounds` animates by default and the animation failed to land — the click reached
the handler, the view simply stayed put. `{animate: false}` fixed it.

**Testing Leaflet is harder than it looks.** Four approaches gave confident wrong
answers before one worked: a synthetic double-click also fires the map's click handler
(so I measured page state, not map state); screenshot comparison conflated tile
loading with view changes; the map pane's CSS transform doesn't change on pure zoom;
tile URLs report stale zoom levels during transitions; and Leaflet's animated zoom
doesn't complete under headless Chrome's virtual clock at all — which made the
*zoom-in button* look broken and sent me after the wrong fault entirely. At one point
a test told me the reset worked when it didn't, and later that it had failed when the
real problem was my zoom step.

Only exposing `window.map`, setting the view with `animate:false` and reading
`map.getZoom()` directly produced a measurement that meant what it claimed.
