## The industrial-overlap bug

`04_extract_industrial_area.py` measured a buffer's industrial area as
`clipped_geom.area.sum()` — summing each polygon's clipped area independently.
OSM maps some industrial land more than once (around station 5627 the estate
"Okhla Ph III" appears as two identical 418,465 m² polygons), so shared land was
counted twice. Overlap is 2.6% of total industrial area in the Delhi extract.

It inflated a feature the model was **trained on**, at 5 of 42 stations — worst
cases 5627 at 0.4481 against a true 0.3147 (+42%) and 6960 at 0.1167 against
0.0698 (+67%).

**Why it survived QC for months, and the lesson.** `05_qc_industrial.py`
hard-fails on `fraction > 1`. With 42 stations none ever crossed it. The
2,388-cell grid is 57× the sample and produced a cell at 1.06, tripping the gate
immediately. The QC was right all along — it just needed a bigger sample. *A
threshold that has never fired is not evidence that it never will.*

Muhammed chose to fix it and re-run rather than keep train/serve consistency and
document (option A over option B). The correction is essentially free:

| spatial LOSO | was | now |
|---|---|---|
| R² | 0.8031 | **0.8018** |
| within-R² | 0.7207 | 0.7156 |
| RMSE µg/m³ | 33.73 | 33.84 |
| conformal q (90%) | 0.5514 | 0.5497 |
| stations below coverage target | 15 | **18** |

**A methodological decision worth flagging.** Keeping the old hyperparameters on
the corrected data scored **0.8035** — better than the re-tuned 0.8018. The
re-tuned figure is kept deliberately: choosing between two hyperparameter
searches by their spatial-LOSO score would reintroduce the test set into model
selection, which is exactly what the block-nested design exists to prevent.
Tuning is seeded, so a fresh clone reproduces 0.8018. The tuning stage was
unfrozen rather than left pinned, because a frozen tuning stage would quietly
break the repo's "reproduces end to end" claim.

## Decisions taken alone, with alternatives

- **1 km, not the planned 5 km slice.** A 5 km extraction produces 1 km-buffer
  features sampled every 5 km — a sparse point sample, not an areal mean, and
  the download design says coarse products are *aggregated* from 1 km cells.
  The slice had already paid for itself. *Rejected:* extract 5 km then redo at
  1 km, two GEE runs for information the first had produced.
- **Batching added to existing extractors, never as copies.** A second copy of a
  feature definition would drift. Default off, so station stages are untouched.
  *Rejected:* prediction-specific extractor scripts.
- **Every batched path verified against the 42 committed station values before
  use.** This caught a first batched-SRTM attempt that read a point value where
  the station script uses a 1 km buffer **mean** — off by up to 7 m. Verified
  versions reproduce to 1e-9 (SRTM), exactly (WorldCover's 12 class counts), and
  3,066/3,066 rows to 1e-12 (NDVI).
- **Per-cell gap-fill calibrations, not borrowed from the nearest station.** The
  method *is* "calibrate at the location you are filling". Borrowing would make
  a cell's AOD depend on its distance from a monitor. *Rejected:* nearest-station
  coefficients.
- **One shared master-table builder**, gaining an optional `--base_table` because
  the grid has no PM2.5 target to define its rows. *Rejected:* a separate
  assembly script, which would have duplicated the NDVI `merge_asof` period join
  — a feature-defining operation.
- **QC bounds overridden, not suppressed**, where station-calibrated thresholds
  are too tight for the grid: a cell at 301.0 m failed a [150, 300] ceiling set
  from 42 urban stations spanning 199.7–271.7 m. It sits on the Aravalli ridge
  and the reading is real, so the grid stage uses 350 m. *Rejected:* removing the
  check, or loosening it for training too.

## Things I got wrong, and what corrected them

- **Overpass.** Four failed attempts before switching to a pre-built Geofabrik
  extract. The decisive evidence arrived early — `out ids` succeeded on the same
  tile where `out geom` returned 504, which already proved the gateway was
  refusing large *responses* rather than timing out on computation. I tuned tile
  size twice more before accepting it.
- **Geofabrik Northern Zone alone.** It excludes Uttar Pradesh, costing 57 power
  plants (including Dadri) and 24% of roads in the Noida/Ghaziabad strip *inside*
  the study bbox. Both would have produced plausible wrong numbers with no error
  anywhere. Caught only by diffing against the training export.
- **MAIAC retry logic.** Retried an identical request four times with backoff on
  the 5000-element error, which is deterministic — the same request can never
  succeed. Replaced with adaptive halving; only 5 of 288 chunks needed it.
- **NDVI diagnosis.** I blamed a 75M-pixel `reduceRegions`. Measurement showed it
  scales sub-linearly; the real cost was `station_fc.geometry().bounds()`, a lazy
  union of 2,388 polygons re-evaluated on all 73 periods. The run was slow, not
  hung, and grep's buffering hid its progress.
- **Extrapolation figure.** I reported 37% of cells outside the training range;
  that was land-use features only. Across all numeric features it is 56%.
- **Near-miss in git.** 549 MB of pbf and 16 MB of chunk cache were about to be
  committed, and a hand-written `.gitignore` had *overwritten* DVC's generated
  one, which would have committed a DVC-managed output and desynchronised the
  two. Caught while staging.

The common thread in the first four: acting before the evidence was exhausted.
The counterweight that caught every real problem was comparing against committed
station values *before* trusting anything.

2. **Extrapolation, which needs a product decision.** 1,334 of 2,388 cells (56%)
   fall outside the training range on at least one feature. Severity, as a
   fraction of the training range's width:

   | | cells | |
   |---|---|---|
   | inside range | 1,054 | 44% |
   | <5% beyond (trivial) | 262 | 11% |
   | 5–25% | 487 | 20% |
   | 25–50% | 249 | 10% |
   | 50–100% | 243 | 10% |
   | >100% (no information) | 93 | 4% |

   So 55% are inside or trivially outside and **585 (25%) are materially
   extrapolating**. `dist_to_nearest_powerplant_km` drives the worst overshoot
   for 537 of them, `slope_deg` for 206. Note `road_density` and `built_up_pct`
   have training *minima* well above zero — every CPCB station is urban — so any
   genuinely rural cell is extrapolation by construction.

   This matters because LightGBM cannot extrapolate (it returns the boundary
   prediction) and the conformal interval was calibrated only at urban stations,
   so neither the estimate nor its interval is validated there. Flags are in
   `reports/prediction/`; how they are surfaced is a product decision.
