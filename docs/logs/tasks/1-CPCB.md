**Study design decisions**
- Study window: March 1, 2025 – February 28, 2026 (full 12-month seasonal cycle), chosen to avoid the OpenAQ CPCB network-wide data discontinuity before Feb 19, 2025
- Season labeling: 4-season CREA/Kumar et al. scheme — summer (Mar–May), monsoon (Jun–Sep), post-monsoon (Oct–Nov), winter (Dec–Feb)

## Key decisions
- **2026-xx-xx** — Chose git (not DVC) for `data/stations/` — these are small, hand-QC'd files that can't be regenerated by rerunning the pipeline, so they need real version history rather than data-versioning.
- **2026-xx-xx** — Study window set to Mar 2025–Feb 2026 specifically to sit after the Feb 19, 2025 OpenAQ CPCB network-wide discontinuity, avoiding a systematic gap at the start of the window.
- **2026-08-17** — Confirmed correct processing order: CPCB completeness QC must run *before* finalizing the station list. Full order: CPCB preprocessing/completeness QC → finalize station list → filter AOD to finalized stations → AOD preprocessing (scale + QA decode) → temporal alignment (CPCB↔AOD join) → MERRA-2 gap-fill → ERA5 extraction → feature assembly.
- **2026-08-19** — Applied the MAIAC overpass window filter (10:30-13:30 IST) to PM2.5 *before* running completeness/QC, not after — full-day metrics don't reflect what the model will actually use.
- **2026-08-19** — Daily aggregation minimum set to 2 overpass hours/day, not 1: a 1-hour "average" gives no noise protection and doesn't guarantee coverage of both MAIAC overpasses (Terra ~10:30, Aqua ~13:30). Cost was only 415 station-days (~2.6%) versus a 1-hour minimum — accepted.
- **2026-08-19** — Station 11607 kept despite partial winter coverage (sensor stopped 2025-12-27): 3 of 4 seasons strong, no stuck/zero problems, judged not worth losing ~7500 good rows over one thin season. Not yet given a dedicated flag column — see Ideas.
- **2026-08-19** — Correlation check's purpose clarified: it tests whether physically close stations' *ground-truth PM2.5* still move together over time (a sanity check on coordinate/instrument correctness), not a multicollinearity concern for the LME — the model's station random intercept already absorbs constant offsets between stations that will share an AOD pixel.
- **2026-08-19** — `12-final_filter.py` reads the station CSV's `status` column directly as the single source of truth for inclusion, replacing the earlier approach of a separate `drop_stations` list in `params.yaml`. The two lists had drifted out of sync (station 301 was marked dropped in the status CSV but `filter_and_aggregate.py`'s hardcoded list still didn't include it, so 301 silently persisted in the daily output) — this is now structurally prevented.

## Data notes & gotchas
- `datetime_from`/`datetime_to` API parameters work; `date_from`/`date_to` are silently ignored on the measurements endpoint (note: `date_from`/`date_to` *did* work on an early `/hours` probe but returned unfiltered/wrong-window data in practice — `datetime_from`/`datetime_to` is the one to trust).
- Network-wide CPCB sensor registration discontinuity starts 2025-02-19 on OpenAQ, regardless of a station's actual history — confirmed both via API and directly on the OpenAQ website, so this is a real OpenAQ coverage gap, not a script bug. Several stations show `datetime_first = 2025-02-19`, an ingestion/registration batch date, **not** true station commissioning.
- Some stations have *multiple* pm25 sensor objects over their lifetime (instrument swaps/re-registrations) — `download_pm25.py` fetches from every sensor overlapping the requested window and stitches them together, not just the first one found.
- Station 5610 (labeled "North Campus, DU" in OpenAQ) is physically located in Patel Nagar per the CPCB CCR dashboard — name is misleading, coordinate verified and accepted as-is.
- Confirmed near-duplicate/shared-pixel clusters (via full pairwise haversine distance, not just nearest-neighbor): **Cluster A** — 5634↔11607 (0.674 km), 5634↔6957 (1.433 km), 6957↔11607 (1.487 km). **Cluster B** — 5610↔5630 (1.278 km), 5404↔5630 (1.32 km). (10900↔10921 at 0.587 km no longer relevant — 10900 dropped.)
- Cluster A daily-PM2.5 correlation is strong (0.85-0.95); Cluster B is moderate (~0.70) — noticeably weaker but not alarming. Worth revisiting if 5610 or 5404 produce surprising residuals once modeling starts.
- Station 6936 looked ~91% complete in its short active window (only Sep-Dec 2025), which hid the real problem: 18.8% of those "present" readings were a stuck sensor. Lesson — completeness alone doesn't catch a frozen sensor; needs the stuck-run check too.
- `params.yaml` values in use: `cpcb_qc.stuck_run_limit` is 3 for window-filtered data (was 5 for full-day data — consecutive rows in windowed data span days, not hours, so a shorter run length is still a meaningful signal).
