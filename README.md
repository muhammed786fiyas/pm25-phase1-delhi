# pm25-phase1-delhi

Satellite-to-ground PM2.5 calibration for Delhi: estimating daily surface PM2.5 at
CPCB monitoring stations from MAIAC satellite aerosol optical depth (AOD),
meteorology and land use.

This is **Phase 1** of a four-city study (Delhi, Mumbai, Chennai, Kolkata). Delhi is
the reference implementation the other cities are replicated from. The whole
pipeline -- data download, QC, feature building and both models -- is tracked with
DVC, so `dvc repro` rebuilds every result from saved data.

## Results

42 CPCB stations, study window 2025-03-01 to 2026-02-28, 13,595 station-days.
Validated by leave-one-station-out cross-validation with a 2 km buffer, so every
number below is a prediction for a station the model never saw. All in raw ug/m3.

| Model | R2 | within-R2 | RMSE (ug/m3) | MAE (ug/m3) |
|---|---|---|---|---|
| **LightGBM** | **0.803** | **0.721** | **33.73** | **20.76** |
| Linear mixed-effects model (LME) | 0.437 | 0.220 | 57.10 | 38.34 |

LightGBM is more accurate at 40 of the 42 stations. The LME is kept for
interpretation: its coefficient table (fitted on log PM2.5) shows how AOD,
season, meteorology and land use relate to PM2.5.

Full detail: `docs/logs/tasks/9-LME_Model.md` and `docs/logs/tasks/10-LightGBM_Model.md`.

## Setup

**1. Clone and create a Python environment** (developed on Python 3.10, also verified
end to end on 3.13):

```bash
git clone https://github.com/muhammed786fiyas/pm25-phase1-delhi.git
cd pm25-phase1-delhi
pip install -r requirements.txt
```

**2. Create a `.env` file** in the repository root. It is gitignored, so it is not
in the clone:

```
MLFLOW_TRACKING_URI=file:./models/mlflow_tracking
OPENAQ_API_KEY=your_key_here
```

`MLFLOW_TRACKING_URI` is required -- the model scripts stop at start-up without it.
`OPENAQ_API_KEY` is only needed to re-download station data (see
[Refreshing the data](#refreshing-the-data)); a free key is available at
https://openaq.org.

**3. Get the data:**

```bash
dvc pull
```

> **Current limitation:** the DVC remote in `.dvc/config` is a folder on the
> author's machine (`E:\PROJECTS\MAIN PROJECTS\INTERNSHIP\CODEBASE`), so `dvc pull`
> only works there. To reproduce on another machine, the data has to be moved to a
> shared remote first (for example Google Drive, S3 or a network folder) with
> `dvc remote add -d <name> <url>` followed by `dvc push`.

## Reproducing the results

```bash
dvc repro      # rebuilds anything out of date
dvc status     # should end with "Data and pipelines are up to date."
```

`dvc status` prints one warning per frozen stage, for example
`WARNING: stage: 'maiac_extract' is frozen`. These are expected -- see below.

If `dvc` is not found on your PATH, use `python -m dvc repro` instead.

## How the pipeline is organised

The full stage graph is in `pipeline_dag.md`. In outline:

```
CPCB ground stations   list -> screen -> download -> QC -> daily aggregate -> completeness -> final roster
Satellite AOD          MAIAC extraction and QC, gaps filled from MERRA-2 with a per-station calibration
Meteorology            ERA5-Land (temperature, humidity, wind) and ERA5 boundary layer height
Land use               ESA WorldCover, Sentinel-2 NDVI, SRTM terrain, OpenStreetMap roads/industry/power plants
Modelling              master feature table -> LME and LightGBM -> spatial cross-validation
```

### Frozen stages

The 12 stages that download from external services -- OpenAQ for station data,
Google Earth Engine for satellite, weather and land-cover data -- are marked
`frozen: true` in `dvc.yaml`. `dvc repro` does not re-run them; it rebuilds
everything downstream from their saved output.

This is deliberate. Both services can revise historical data, so re-downloading
could quietly change the results. The saved snapshot is what makes them
reproducible, and it also saves hours per run.

A frozen stage ignores changes to its inputs. If the station list or its
coordinates change, unfreeze the affected stages, re-run, and freeze them again.

### Refreshing the data

```bash
dvc unfreeze cpcb_download_pm25      # or any other frozen stage
dvc repro cpcb_download_pm25         # re-download
dvc freeze cpcb_download_pm25        # freeze the new snapshot
dvc repro                            # rebuild everything downstream of it
```

Earth Engine stages also need `earthengine authenticate` and access to the
`internship-pm25` Earth Engine project.

### The station list

`data/stations/cpcb_stations_delhi_status.csv` decides which stations are used
(`status == KEEP`). It is **generated by the pipeline -- do not edit it by hand.**

- `cpcb_screen_stations` drops stations that cannot be used before any data is
  downloaded: no records at all, records that end before or start after the study
  window, and duplicate sites at identical coordinates.
- `cpcb_finalize_roster` then keeps stations with at least 60% of days covered and
  drops the rest.

To drop or keep a station for a reason the rules do not cover, add a row to
`data/stations/cpcb_station_overrides_delhi.csv` (`location_id,status,reason`).
That file is applied last and is never overwritten. It is empty for Delhi: the
rules reproduce the original hand-curated list of 42 stations exactly.

## Repository layout

```
params.yaml           tunable settings (thresholds, windows, model options)
dvc.yaml              every pipeline stage: command, inputs, outputs
scripts/datasets/     download and QC scripts, one folder per data source
scripts/modeling/     dataset preparation, LME, LightGBM
data/                 raw -> interim -> processed data (DVC-tracked)
data/stations/        the station list, its screening, and the overrides file
models/               fitted models; models/mlflow_tracking/ is the MLflow store
reports/              coefficient tables, feature importance, cross-validation results
docs/logs/            task logs (one per module) and daily work logs
```

## Notes

- `pipeline_dag.md` should be UTF-8. Regenerating it with PowerShell's `>` redirect
  writes UTF-16 instead; write it through Python or from Git Bash:
  `python -m dvc dag --md > pipeline_dag.md`
- Experiment runs are logged to MLflow under `models/mlflow_tracking/`. MLflow 3
  refuses this file-based store unless `MLFLOW_ALLOW_FILE_STORE=true` is set (the
  pipeline scripts set it themselves). To browse the runs:

  ```bash
  # PowerShell
  $env:MLFLOW_ALLOW_FILE_STORE = "true"
  mlflow ui --backend-store-uri file:./models/mlflow_tracking

  # Git Bash / Linux / macOS
  MLFLOW_ALLOW_FILE_STORE=true mlflow ui --backend-store-uri file:./models/mlflow_tracking
  ```
